# Task 4. Проектирование продажи ОСАГО

Доработка схемы из Task 3: добавлен сервис **osago-aggregator** и поток онлайн-оформления ОСАГО.
Схема: `InsureTech_C4_container_osago.drawio` (нотация C4, открывается в draw.io).

## Пользовательский сценарий
1. Клиент в Web App заполняет заявку об автомобиле → `POST` в `core-app` (REST).
2. `core-app` (оркестратор ОСАГО) инициирует агрегацию: `POST /osago-requests` в `osago-aggregator`.
3. `osago-aggregator` рассылает заявку во все страховые компании (×10) и опрашивает решения (≤60 с на компанию).
4. Каждое пришедшее предложение `osago-aggregator` публикует в Kafka (`osago-offers`); `core-app`
   потребляет и **сразу** толкает его в браузер по **SSE** — предложения появляются по мере поступления.

Требования: макс. ожидание от компании **60 с**, пик **2500** одновременных пользователей.
Бизнес-логика ОСАГО остаётся в `core-app`; `osago-aggregator` отвечает только за взаимодействие со
страховыми компаниями.

---

## Ответы по пунктам задания

### 1. Реализация osago-aggregator
Для каждой заявки выполняет fan-out «создать заявку» во все СК, затем независимый опрос «получить
предложение» по каждой компании (до 60 с). Полученные предложения передаёт в `core-app` по мере
поступления (не дожидаясь остальных). Взаимодействие с каждой СК защищено паттернами устойчивости
(см. п.7) и изолировано по компаниям (Bulkhead).

### 2. Требуется ли своё хранилище данных — ДА
`osago-aggregator` — stateful (long-running опрос ≤60 с). Своё хранилище (**Redis**, при необходимости
+ схема PostgreSQL) нужно для:
- состояния незавершённых заявок и того, какие СК ещё опрашиваются;
- сохранённых предложений до передачи в `core-app` (без дублей);
- **идемпотентности** — не создать повторную заявку в СК при ретраях;
- переживания рестартов (любой экземпляр может продолжить опрос);
- **общего между экземплярами** состояния: распределённые счётчики Circuit Breaker и Rate Limiter.

### 3. Какой API osago-aggregator предоставляет core-app
- `POST /osago-requests` `{applicationId, carInfo, companies[]}` → `202 Accepted {aggregationId}` —
  инициировать агрегацию (быстрый ответ, без ожидания 60 с).
- `GET /osago-requests/{aggregationId}` — статус/добор (восстановление).
- Сами предложения **не отдаются синхронно** — они стримятся асинхронно событиями (см. п.4).

### 4. Средство интеграции core-app ↔ osago-aggregator
- **Инициация** — синхронный **REST** (`POST /osago-requests`): `core-app` получает `aggregationId`
  и не блокируется на 60 с.
- **Поток предложений обратно** — **асинхронно через Kafka**, топик `osago-offers` (консистентно с
  EDA из Task 3). Инкрементальная доставка по мере ответов СК; партиционирование по `requestId`.

### 5. API для веб-приложения в core-app
- `POST /osago/applications` (REST) → `{requestId}` — отправить заявку.
- `GET /osago/applications/{requestId}/offers/stream` — **SSE** (`text/event-stream`): пушит каждое
  предложение по мере поступления.
- `GET /osago/applications/{requestId}/offers` (REST) — добор предложений при переподключении.

### 6. Средство интеграции веб ↔ core-app
REST (отправка заявки) **+ SSE** (стрим предложений). SSE отличается от REST → на схеме отражён
**отдельной (оранжевой пунктирной) стрелкой** `core-app → Web App`.

**Почему SSE, а не WebSockets:** поток предложений строго однонаправленный (server→client,
display-only) — обратный канал от клиента не нужен. SSE проще WebSockets, имеет встроенное
переподключение (Last-Event-ID), не блокируется корпоративными FW/proxy (работает как обычный HTTP).
WebSockets (full-duplex, бинарь) здесь избыточен и сложнее масштабируется. GraphQL Subscriptions не
подходит — у core-app нет GraphQL API (он появляется в Task 5 у client-info).

### 7. Паттерны отказоустойчивости (где применяются)
**osago-aggregator → каждая страховая компания** (ненадёжный внешний REST):
- **Timeout 60 с** — overall на компанию (бизнес-требование), fail-fast по истечении.
- **Retry** — exponential backoff + jitter на транзиентные ошибки; только идемпотентно / по ключу
  идемпотентности (чтобы не плодить заявки).
- **Circuit Breaker** — на каждую СК отдельно (Closed→Open→Half-Open): «мёртвую» компанию не
  опрашиваем 60 с, отказываем быстро.
- **Rate Limiting** — на каждую СК (Token Bucket): соблюдаем лимиты API компаний и гасим всплеск 2500.
- **Bulkhead** — изоляция пула соединений/тредов по компаниям: медленная СК не вытесняет остальные.

**core-app → osago-aggregator** (REST-инициация): **Timeout + Retry + Circuit Breaker**.

**Веб/партнёры → core-app**: **Rate Limiting** на **API Gateway / L7-балансировщике** (узел добавлен на
схему) — защита от пика 2500 одновременных пользователей.

*(На схеме паттерны показаны метками-«пилюлями», прикреплёнными непосредственно К защищаемым рёбрам
`osago-aggregator → СК`, `core-app → osago-aggregator` и `API Gateway → core-app`.)*

### 8. Сервисы в нескольких экземплярах — решение зависит, учтено
- **Маршрутизация SSE.** Предложение должно дойти до того экземпляра `core-app`, который держит
  SSE-соединение пользователя. Решение: **sticky sessions** на L7-балансировщике (по сессии/requestId)
  и/или общий pub/sub — все экземпляры `core-app` подписаны на `osago-offers`, фильтруют по
  `requestId`/сессии и толкают в своё соединение; партиционирование топика по `requestId`.
- **osago-aggregator в нескольких экземплярах.** Состояние опроса — в общем хранилище (Redis/БД), чтобы
  любой экземпляр мог продолжить. **Circuit Breaker и Rate Limiter — распределённые** (Redis): иначе N
  экземпляров суммарно превысят лимиты СК и будут иметь рассинхронизированные состояния. **Ключи
  идемпотентности** опроса исключают дублирование заявок в СК.

## Трактовка «сохранить подход» (решение команды п.1)
«Сохранить подход, использованный для продуктов/тарифов» трактуется как: (а) поток продуктов/тарифов
из Task 3 (событийный, через `insurance-products-updated`) **не меняется**; (б) для нового потока
ОСАГО-предложений переиспользуется тот же механизм Kafka/EDA (топик `osago-offers`). Это НЕ означает
загонять ОСАГО в модель 15-минутного опроса с репликой — требование реального времени (≤60 с,
показ по мере поступления) этого не допускает.
