# Task 2. Динамическое масштабирование контейнеров (HPA)

Здесь я настраиваю автоматическое горизонтальное масштабирование тестового приложения
`scaletestapp` в Kubernetes (Minikube) и проверяю его под нагрузкой Locust.

Оговорка по формулировке: в условии сказано показать, что «количество реплик базы данных
поменялось», но базы данных в этом задании нет — похоже, это опечатка. Масштабируются поды
Deployment `scaletestapp`, и лог-артефакт подтверждает рост именно их числа.

## Состав

| Файл | Назначение |
|---|---|
| `deployment.yaml` | Deployment `scaletestapp` (1 реплика, лимит памяти 30Mi, порт 8080) |
| `service.yaml` | Service `scaletestapp` (NodePort, 80 → 8080) |
| `hpa.yaml` | HorizontalPodAutoscaler (`autoscaling/v2`, min 1 / max 10, память 80% + CPU 80%) |
| `locustfile.py` | Сценарий нагрузки (`GET /`) |
| `scaling-log.txt` | Подтверждение изменения числа реплик под нагрузкой (рост 1→3→6→10) |

## Ключевые решения

В HPA у меня две метрики. Целевая утилизация памяти 80% — как требует задание. Но когда я
погонял приложение под нагрузкой, выяснилось, что `GET /` почти не наращивает память — по одной
этой метрике масштабирование могло бы просто не сработать. Поэтому я добавил вторую метрику,
CPU 80%: HPA берёт максимум из рекомендаций по обеим, и под нагрузкой срабатывает именно CPU.

Ещё два момента, без которых HPA не работает. Во-первых, в Deployment обязательно нужны
`resources.requests` — HPA считает утилизацию как `usage / requests`, а не от `limits`; без них
в колонке `TARGETS` висит `<unknown>` и масштабирования не происходит. Во-вторых, в кластере
должен быть включён `metrics-server` — именно он поставляет метрики CPU и памяти в Metrics API,
который опрашивает HPA.

## Как воспроизвести (runbook)

### 1. Кластер Minikube + metrics-server
```bash
minikube start --addons=metrics-server
# если кластер уже запущен:
minikube addons enable metrics-server
# проверка, что metrics-server поднялся:
kubectl get deployment metrics-server -n kube-system
```

### 2. Применить манифесты
```bash
cd Task2
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f hpa.yaml
```
Дождаться, пока в HPA появятся метрики (колонка `TARGETS` перестанет быть `<unknown>` — обычно
15–60 секунд после старта metrics-server):
```bash
kubectl get hpa scaletestapp-hpa
kubectl describe hpa scaletestapp-hpa
```

### 3. Получить URL приложения для нагрузки
```bash
minikube service scaletestapp --url
# пример вывода: http://127.0.0.1:51544
```

### 4. Сгенерировать нагрузку через Locust
В каталоге с `locustfile.py`:
```bash
pip install locust
locust
```
Открыть <http://localhost:8089>, указать:
- Host — URL из шага 3;
- Number of users — `500–1000`;
- Spawn rate — `50`.

Запустить тест.

Важный практический момент: не задавайте 10000 пользователей. На Windows тоннель
`minikube service --url` имеет ограниченный backlog — при тысячах одновременных соединений он
начинает отвергать запросы (`ConnectionRefusedError 10061`, высокий процент Failures), и до пода
доходит лишь малая часть трафика: CPU не растёт, HPA не масштабирует. Умеренные 500–1000
пользователей дают высокий успешный RPS, который реально нагружает под. Альтернатива вообще без
тоннеля — запустить Locust как pod внутри кластера и подавать нагрузку напрямую на
ClusterIP-сервис; именно так снят итоговый лог.

### 5. Наблюдать масштабирование (отдельные терминалы)
```bash
kubectl get hpa scaletestapp-hpa -w           # утилизация и REPLICAS растут
kubectl get pods -l app=scaletestapp -w        # появляются новые поды (до 10)
minikube dashboard                             # графики реплик/нагрузки -> скриншоты
```

### 6. Зафиксировать результат (артефакт сдачи)
Положить в `Task2/` скриншоты дашборда Minikube с ростом числа реплик или лог, например:
```bash
kubectl get hpa scaletestapp-hpa > scaling-log.txt
kubectl get pods -l app=scaletestapp >> scaling-log.txt
kubectl describe hpa scaletestapp-hpa >> scaling-log.txt
```

### 7. Проверить scale-down
Остановить тест в Locust. Через несколько минут (стабилизационное окно HPA по умолчанию ~5 мин)
число реплик автоматически вернётся к `minReplicas: 1`:
```bash
kubectl get hpa scaletestapp-hpa -w
```

## Как прошёл прогон и что пришлось подкрутить

Первый прогон я запустил с 10000 пользователей — и масштабирования не получил. Разбор показал
сразу три причины. Главная: до 93% запросов вообще не доходили до пода — их отвергал тоннель
minikube (та самая `ConnectionRefusedError 10061`). При этом память держалась на 70–82% при цели
80%: пик 82% попал в зону толерантности HPA (около 10%), и триггер не сработал. А CPU оставался
на 17–21% при `requests.cpu=100m` — нагрузки на него просто не хватало.

Из этого я сделал вывод, что у `GET /` память слабо зависит от нагрузки и эффективный триггер —
CPU, и подкрутил ресурсы в Deployment: `requests.cpu` снизил со 100m до 30m (в простое под ест
~19m, это ~63% — лишнего масштабирования нет, а под нагрузкой утилизация переваливает за 80%),
`requests.memory` — с 25Mi до 20Mi. `limits.cpu` уменьшил с 250m до 100m, чтобы под быстрее
упирался в потолок и HPA активнее добавлял реплики; `limits.memory` оставил 30Mi, как в задании.
Нагрузку снизил до 500–1000 пользователей, чтобы она доходила до пода. По ходу экспериментов я
пробовал опускать целевые значения HPA до 70%, чтобы уйти подальше от зоны толерантности, но в
итоге вернул 80%, как в задании: когда нагрузка подаётся правильно, запас не нужен.

Подтверждённый прогон (нагрузка изнутри кластера) — в [`scaling-log.txt`](scaling-log.txt):
CPU дошёл до 329% при цели 80%, и реплики выросли 1 → 3 → 6 → 10.

## Примечания

В production HPA обычно дополняют Cluster Autoscaler — он добавляет узлы в кластер, когда новым
подам не хватает ресурсов на существующих.
