## Проблемы as-is → решения to-be

| Проблема (as-is) | Решение (to-be) |
|---|---|
| Медленные страницы под нагрузкой (поиск 50 RPS, оформление 10 RPS) | Горизонтальное масштабирование сервисов (K8s + HPA), L7-балансировка, CDN для статики |
| Нарушение SLA из-за «шумного соседа» (партнёр 250 RPS вместо 20) | **API Gateway + Rate Limiting**: квота 20 RPS/партнёр, изоляция ресурсов (Bulkhead) |
| Падения, узнают от пользователей; 500 тыс ₽/час | **Prometheus + Grafana + Alertmanager** — проактивный мониторинг и алерты |
| Один K8s-кластер в одной зоне (SPOF) | **3 зоны доступности, Active-Active**, независимые кластеры |
| PostgreSQL в единственном экземпляре (SPOF) | **PostgreSQL + Patroni**: Primary + 2 реплики, авто-failover, бэкап в S3 |

## 1. Стратегия масштабирования и отказоустойчивости

**Горизонтальное vs вертикальное.** Для stateless-сервисов (`core-app`, `client-info`,
`ins-product-aggregator`, `ins-comp-settlement`) выбрано **горизонтальное** масштабирование:
добавление подов (K8s HPA) и узлов/зон. Это эффективнее при росте RPS и числа пользователей, чем
вертикальное (упирается в потолок одной машины и не повышает отказоустойчивость). Вертикальное
масштабирование применяется **дополняюще** к БД (ресурсы Primary) — у БД горизонтальное
масштабирование записи ограничено.

**Нужны ли дополнительные зоны безопасности — да.** Целевая доступность **99,9%** недостижима в
одной зоне (отказ зоны = полный простой). По классификации доступности уровень ≥99,5% требует
схемы **Active-Active**, а она реализуется только при географической/зональной избыточности.
Дополнительно несколько зон обеспечивают равномерную латентность для пользователей из разных
регионов РФ. Выбрано **3 зоны** (нечётное число — необходимо для кворума etcd в Patroni и в
control-plane).

**Стратегия: Active-Active.** Все три зоны одновременно обслуживают трафик. Резервирование мощности
по правилу **50% утилизации**: при отказе одной из зон оставшиеся принимают её нагрузку без
деградации.

## 2a. Конфигурация Kubernetes: независимые кластеры (не stretched)

Выбраны **независимые кластеры K8s в каждой зоне**, а не один растянутый (stretched).

**Почему.** Stretched-кластер держит единый control-plane и etcd, распределённые между зонами, и
требует стабильной low-latency сети. Сетевой раздел (network partition) между зонами ломает кворум
etcd и способен положить **весь** control-plane — это противоречит цели отказоустойчивости.
Независимые кластеры **самоизолируются**: отказ или раздел одной зоны не затрагивает остальные;
переключение трафика берёт на себя GSLB на уровне выше. Управление единообразием конфигураций
решается на уровне CI/CD и GitOps, а не общим control-plane.

*(Комментарий продублирован на схеме рядом с зонами.)*

## 2b. Балансировка нагрузки и health-checks

Двухуровневая балансировка:

1. **Глобальный уровень — GSLB / Yandex Cloud DNS.** Распределяет клиентов по зонам с учётом
   географии (минимальная латентность) и состояния зон. Постоянно опрашивает **health-check**
   каждой зоны; нездоровые зоны исключаются из ротации.
2. **Локальный уровень — L7 Load Balancer (Application LB)** в каждой зоне. Распределяет трафик
   между подами K8s, выполняет **health-check подов** (liveness/readiness) и не направляет запросы
   на неготовые экземпляры.

**API Gateway** перед сервисами реализует **Rate Limiting** для B2B-партнёров (квота 20 RPS на
партнёра, Token Bucket) — закрывает проблему «шумного соседа». Партнёрский трафик больше не идёт
напрямую в K8s LoadBalancer.

**CDN (Yandex CDN)** кэширует статику веб-приложения на edge-узлах — одинаковое время загрузки
страниц независимо от региона.

Все health-check явно отражены на схеме (пунктирные стрелки от GSLB к зонам и подпись health-check
у L7-балансировщиков).

## 2c. Фейловер-стратегия (уровень клиент ↔ приложение)

**Active-Active с health-based DNS-failover на GSLB.**

- В штатном режиме клиент попадает в ближайшую здоровую зону.
- GSLB проверяет health-check зон каждые ~10 с. При отказе зоны она исключается из DNS-ответов, и
  новые клиенты направляются в здоровые зоны. Низкий TTL DNS обеспечивает быстрое переключение.
- Так как все зоны активны, **отсутствует «холодный старт»** резерва — переключение укладывается
  далеко в рамки **RTO 45 мин**.

Стратегия отражена на схеме на уровне взаимодействия клиента с приложением (клиенты → GSLB → зоны).

## 2d. Конфигурация базы данных (RTO 45 мин / RPO 15 мин)

**СУБД: PostgreSQL. Фреймворк HA-кластера: Patroni** (отражён на схеме).

**Топология:**
- **1 Primary + 2 реплики**, по одному узлу PostgreSQL в каждой зоне.
- **etcd-ансамбль (3 узла)** — распределённое хранилище состояния (DCS) и выбор лидера Patroni.
- **HAProxy** — маршрутизирует подключения приложений на текущий Primary (читает лидера из etcd).

**Репликация:**
- **Синхронная** репликация на ближайшую реплику (Зона B) ⇒ при отказе зоны Primary потеря данных
  ≈ 0 (**RPO≈0** для зонального сбоя).
- **Асинхронная** реплика (Зона C) — дополнительный резерв чтения и геоустойчивости.

**Резервное копирование:**
- **pgBackRest** — полные/инкрементальные бэкапы + непрерывное **архивирование WAL в
  Yandex Object Storage (S3)** с интервалом ≤ 5 мин ⇒ **RPO ≤ 15 мин** даже при полной потере
  кластера (PITR-восстановление).

**Соответствие RTO 45 мин:**
- Авто-failover Patroni при отказе Primary ≈ 30 с (новый лидер из синхронной реплики).
- Полное восстановление из S3 для объёма 50 GB укладывается значительно быстрее 45 мин.

## 3. Шардирование БД

**Решение: шардирование НЕ применяется.** (Отражено на схеме отдельным комментарием.)

**Обоснование.** Объём данных **50 GB** многократно ниже порога целесообразности шардирования —
один Primary спокойно обслуживает такой объём. Шардирование — **необратимое** усложнение
(маршрутизация по ключу, ребалансировка, потеря части кросс-шардовых запросов/транзакций), которое
вводить преждевременно вредно. Масштабирование **чтения** обеспечивается репликами. Решение
подлежит пересмотру при существенном росте данных (ориентир ~150+ GB или рост write-нагрузки на
Primary).

## Итоговый состав решения (на схеме)

- **Edge:** GSLB (Yandex Cloud DNS) + CDN.
- **3 зоны (Active-Active), независимые кластеры K8s**, в каждой: L7 LB → API Gateway (Rate
  Limiting) → сервисы (core-app, client-info, ins-product-aggregator, ins-comp-settlement) с HPA.
- **Данные:** PostgreSQL + Patroni (Primary + sync/async реплики), etcd-кворум, HAProxy,
  pgBackRest → Object Storage (S3).
- **Наблюдаемость:** Prometheus + Grafana + Alertmanager.
- **Без шардирования** (50 GB).
