# Task 1. Технологическая архитектура InsureTech (to-be)

Схема решения — **`InsureTech_технологическая_архитектура_to-be.drawio`** (открывается в
[draw.io](https://app.diagrams.net)). Ниже я объясняю решения, которые на ней отражены,
по пунктам задания.

Про нотацию: схему я собрал базовыми фигурами draw.io (боксы, цилиндры, комментарии), иконки
Yandex Cloud не подставлял — структура, связи и подписи те же, что были бы с иконками, так что
при необходимости они меняются точечно.

## Требования бизнеса

| Параметр | Значение |
|---|---|
| Доступность (Availability) | 99,9% (≈8,76 ч простоя/год) |
| RTO (время восстановления) | 45 мин |
| RPO (допустимая потеря данных) | 15 мин |
| География | Все часовые пояса РФ, рост в регионах |
| Время загрузки страниц | Одинаковое независимо от региона |
| Объём данных | 50 GB |

## Проблемы as-is и что я с ними делаю

| Проблема (as-is) | Решение (to-be) |
|---|---|
| Медленные страницы под нагрузкой (поиск 50 RPS, оформление 10 RPS) | Горизонтальное масштабирование сервисов (K8s + HPA), L7-балансировка, CDN для статики |
| Нарушение SLA из-за «шумного соседа» (партнёр 250 RPS вместо 20) | API Gateway с Rate Limiting: квота 20 RPS на партнёра, изоляция ресурсов (Bulkhead) |
| Падения, о которых узнают от пользователей; 500 тыс ₽/час | Prometheus + Grafana + Alertmanager — проактивный мониторинг и алерты |
| Один K8s-кластер в одной зоне (единая точка отказа) | Три зоны доступности, Active-Active, независимые кластеры |
| PostgreSQL в единственном экземпляре (единая точка отказа) | PostgreSQL + Patroni: Primary и две реплики, авто-failover, бэкап в S3 |

## 1. Стратегия масштабирования и отказоустойчивости

Сначала про выбор между вертикальным и горизонтальным масштабированием. Все четыре сервиса
(`core-app`, `client-info`, `ins-product-aggregator`, `ins-comp-settlement`) — stateless, поэтому
для них я выбрал **горизонтальное**: добавлять поды через HPA и узлы по зонам. При росте RPS это
эффективнее вертикального, которое рано или поздно упирается в потолок одной машины и при этом
никак не повышает отказоустойчивость. Вертикальное масштабирование у меня остаётся только как
дополнение для БД — наращивать ресурсы Primary, потому что запись в реляционной базе горизонтально
масштабируется плохо. Причём нарастить Primary можно без простоя: увеличить ресурсы реплики и
промоутить её в Primary через управляемый switchover Patroni.

Дополнительные зоны доступности нужны. Целевые 99,9% в одной зоне недостижимы в принципе — отказ
зоны означает полный простой. По классификации доступности уровень от 99,5% требует схемы
**Active-Active**, а она реализуема только при зональной или географической избыточности. Бонусом
несколько зон дают равномерную латентность для пользователей из разных регионов РФ. Я взял **три
зоны** — нечётное число нужно для кворума etcd (и в Patroni, и в control-plane).

Все три зоны обслуживают трафик одновременно. Мощность резервирую по правилу 50% утилизации: если
одна зона упадёт, оставшиеся две примут её нагрузку без деградации.

## 2a. Kubernetes: независимые кластеры, а не растянутый

В каждой зоне — свой независимый кластер K8s, а не один stretched на все три.

Формально растянуть кластер можно: зоны одного региона связаны низколатентной сетью. Но единый
control-plane на все зоны увеличивает blast-radius — его проблема или неудачное обновление бьёт
сразу по всем зонам, и невозможно катить обновления по зонам независимо. Независимые кластеры
самоизолируются: отказ, плохой rollout или сетевой раздел одной зоны не задевает остальные, а
переключение трафика забирает на себя GSLB уровнем выше. Единообразие конфигураций при этом
обеспечивается через CI/CD и GitOps, а не через общий control-plane.

Может показаться, что это противоречит растянутому etcd-кворуму Patroni из пункта 2d — но
противоречия нет. etcd у Patroni пишет редко (только смена лидера и конфигурации), зоны региона
низколатентны, поэтому растянутый кворум из трёх узлов корректен и переживает отказ зоны. Против
растянутого K8s работает не аргумент «сеть/кворум», а изоляция blast-radius большого изменчивого
control-plane — у компактного etcd-ансамбля Patroni этой проблемы нет.

Этот комментарий продублирован на схеме рядом с зонами.

## 2b. Балансировка нагрузки и health-checks

Балансировка двухуровневая:

1. **Глобальный уровень — GSLB (Yandex Cloud DNS).** Распределяет клиентов по зонам с учётом
   географии (минимальная латентность) и состояния зон: постоянно опрашивает health-check каждой
   зоны и исключает нездоровые из ротации.
2. **Локальный уровень — L7-балансировщик (Application LB)** в каждой зоне. Распределяет трафик
   между подами, проверяет их liveness/readiness и не отправляет запросы на неготовые экземпляры.

Перед сервисами стоит **API Gateway** с Rate Limiting для B2B-партнёров — квота 20 RPS на партнёра
по Token Bucket. Это закрывает проблему «шумного соседа»: партнёрский трафик больше не идёт
напрямую в K8s LoadBalancer.

Статику веб-приложения кэширует **CDN (Yandex CDN)** на edge-узлах — за счёт этого время загрузки
страниц не зависит от региона пользователя.

Все health-check явно показаны на схеме: пунктирные стрелки от GSLB к зонам и подписи health-check
у L7-балансировщиков.

## 2c. Фейловер-стратегия (уровень клиент ↔ приложение)

Я выбрал Active-Active с health-based DNS-фейловером на GSLB.

В штатном режиме клиент попадает в ближайшую здоровую зону. GSLB опрашивает health-check зон
примерно раз в 10 секунд; отказавшая зона исключается из DNS-ответов, и новые клиенты уходят в
здоровые. Низкий TTL DNS ускоряет переключение. Поскольку все зоны и так активны, «холодного
старта» резерва нет вообще — переключение укладывается в RTO 45 минут с огромным запасом.

Для уже подключённых пользователей полагаться на обновление DNS нельзя — TTL кэшируется. Поэтому
на клиенте используется несколько A-записей плюс retry с таймаутом: при ошибке обращения к одной
зоне клиент немедленно повторяет запрос в другую, не дожидаясь DNS. Это и есть фейловер именно на
уровне взаимодействия клиента с приложением; на схеме он показан в цепочке «клиенты → GSLB → зоны».

## 2d. Конфигурация базы данных (RTO 45 мин / RPO 15 мин)

СУБД — PostgreSQL, HA-кластер собран на **Patroni** (фреймворк отражён на схеме).

Топология: один Primary и две реплики, по узлу PostgreSQL в каждой зоне. Состояние кластера и
выбор лидера — в etcd-ансамбле из трёх узлов (DCS для Patroni). Приложения подключаются через
HAProxy, который читает из etcd, кто сейчас Primary, и маршрутизирует соединения на него.

Репликация комбинированная. На ближайшую реплику (зона B) — **синхронная**: при отказе зоны
Primary данные не теряются, RPO для зонального сбоя практически нулевой. Реплика в зоне C —
**асинхронная**, как дополнительный резерв чтения и геоустойчивости.

Резервное копирование — **pgBackRest**: полные и инкрементальные бэкапы плюс непрерывное
архивирование WAL в Yandex Object Storage (S3) с интервалом до 5 минут. Даже при полной потере
кластера восстановление через PITR теряет не больше 15 минут данных — требование RPO выполняется.

По RTO: авто-failover Patroni при отказе Primary занимает около 30 секунд (лидером становится
синхронная реплика), а полное восстановление 50 GB из S3 укладывается в 45 минут с запасом.

## 3. Шардирование БД

Шардирование я **не применяю** — на схеме это отмечено отдельным комментарием.

Объём данных 50 GB многократно ниже порога, где шардирование имеет смысл: такой объём спокойно
обслуживает один Primary. При этом шардирование — практически необратимое усложнение: маршрутизация
по ключу, ребалансировка, потеря части кросс-шардовых запросов и транзакций. Вводить его
преждевременно вредно. Масштабирование чтения уже закрыто репликами. К решению стоит вернуться,
если данные вырастут примерно до 150+ GB или заметно вырастет write-нагрузка на Primary.

## Итоговый состав решения (на схеме)

- Edge: GSLB (Yandex Cloud DNS) + CDN.
- Три зоны в Active-Active, в каждой — независимый кластер K8s: L7 LB → API Gateway
  (Rate Limiting) → сервисы core-app, client-info, ins-product-aggregator, ins-comp-settlement
  с HPA.
- Данные: PostgreSQL + Patroni (Primary, синхронная и асинхронная реплики), etcd-кворум, HAProxy,
  pgBackRest → Object Storage (S3).
- Наблюдаемость: Prometheus + Grafana + Alertmanager.
- Шардирование не применяется (50 GB).
