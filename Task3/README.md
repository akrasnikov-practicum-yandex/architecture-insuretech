# Task 3. Переход на Event-Driven архитектуру

Решение по устранению проблем синхронной интеграции (см. `problems-and-risks.md`) и обновлённая
диаграмма контейнеров `InsureTech_C4_container_to-be.drawio` (нотация C4, открывается в draw.io).

Декомпозиция функциональности между сервисами **не меняется** — меняется только способ их
взаимодействия.

## Что переведено на Event-Streaming (Apache Kafka)

| Было (as-is) | Стало (to-be) |
|---|---|
| `core-app` опрашивает `ins-product-aggregator` по REST раз в 15 мин | `core-app` подписан на топик `insurance-products-updated`, обновляет локальную реплику по событиям |
| `ins-comp-settlement` опрашивает `ins-product-aggregator` по REST раз в сутки | `ins-comp-settlement` подписан на тот же топик (отдельная consumer-group) |
| `ins-comp-settlement` тянет из `core-app` оформленные страховки по REST раз в сутки | `core-app` публикует события `PolicyIssued` в топик `policies-issued`; settlement потребляет near-real-time |
| `ins-product-aggregator` синхронно опрашивает все компании в пути запроса | плановый/фоновый опрос компаний; результат публикуется в `insurance-products-updated` (медленная компания не блокирует потребителей) |

**Топики Kafka:**
- `insurance-products-updated` — producer: `ins-product-aggregator`; consumers: `core-app`, `ins-comp-settlement`.
- `policies-issued` — producer: `core-app`; consumer: `ins-comp-settlement`.

Партиционирование по `insurance_company_id` сохраняет порядок событий в разрезе компании.

## Почему Apache Kafka, а не RabbitMQ
- Неизменяемый **воспроизводимый лог** — потребитель может перечитать историю и восстановить реплику.
- Несколько **независимых** consumer-group: добавить нового потребителя (аналитика, антифрод) можно
  без изменений у producer'а.
- Высокая пропускная способность и горизонтальное масштабирование при росте до 10+ компаний.
- Модель «глупый брокер — умный потребитель» с управлением offset на стороне consumer'а.

RabbitMQ удаляет сообщения после доставки и не даёт реплея/истории — для обновления реплик и
аудита он подходит хуже.

## Решение по Transactional Outbox — ДА

Применяется в сервисах, которые одновременно пишут в свою БД и публикуют событие — это
**проблема двойной записи** (БД-запись и публикация в брокер должны произойти атомарно):

- **`core-app`** — при оформлении страховки в одной транзакции пишет полис в БД **и** запись в
  `outbox` (событие `PolicyIssued`).
- **`ins-product-aggregator`** — при обновлении продуктов/тарифов в одной транзакции пишет данные
  **и** `outbox`-запись (`ProductUpdated`).

**Relay (доставка из outbox в Kafka):** по умолчанию **Polling Publisher** (периодическая вычитка
`status='PENDING'`); как low-latency альтернатива на схеме отмечен **CDC через Debezium**
(Transaction Log Tailing по WAL).

**Гарантии:** Kafka обеспечивает доставку **at-least-once**, поэтому потребители **идемпотентны** —
дедупликация по `event_id` (таблица обработанных событий). Это исключает двойное применение события
к реплике.

## Что осталось синхронным (REST) — намеренно
- `Web App → core-app` и `core-app ↔ client-info` — пользовательские сценарии, синхронный ответ нужен.
- `ins-product-aggregator → страховые компании` — внешние REST API компаний; вынесены из пути
  запроса в фоновый опрос.
- `ins-comp-settlement → страховые компании` — месячный реестр премий (batch), изменение не требуется.

## Эффект
- Устранены каскадные задержки и зависимость потребителей от доступности аггрегатора/компаний.
- Реплики обновляются near-real-time, с гарантией доставки и возможностью реплея.
- Сервисы масштабируются и развиваются независимо; добавление компаний не затрагивает потребителей.
