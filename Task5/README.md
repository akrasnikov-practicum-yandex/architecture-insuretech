# Task 5. GraphQL API для client-info

Перевод REST API сервиса `client-info` на GraphQL. Схема: **`client-info.graphql`** (SDL).

## Проблема исходного REST API
Карточка клиента содержит до ~500 атрибутов, а потребители (веб-приложение, `core-app`) в разных
сценариях запрашивают разные подмножества данных. REST оставляет два неудачных полюса:
- **множество узких ресурсов** (контакты, документы, родственники отдельно) — в одном сценарии нужно
  несколько объектов, их тянут разными запросами ⇒ кратный рост RPS;
- **один «толстый» ресурс** со всеми данными — over-fetching, большой объём, замедление (особенно для веба).

GraphQL даёт **один эндпоинт** и позволяет потребителю **выбрать ровно нужные поля** в одном запросе.

## Анализ исходного контракта (Swagger)
| REST-операция | Возвращает | Тип |
|---|---|---|
| `GET /clients/{id}` | клиент | `Client { id, name, age }` |
| `GET /clients/{id}/documents` | список документов | `Document { id, type, number, issueDate, expiryDate }` |
| `GET /clients/{id}/relatives` | список родственников | `Relative { id, relationType, name, age }` |

Все операции — только чтение ⇒ в GraphQL достаточно `Query` (мутации/подписки контрактом не предусмотрены).

## Маппинг REST → GraphQL
| REST-операция | GraphQL |
|---|---|
| `GET /clients/{id}` | `query { client(id: ID!) { ... } }` |
| `GET /clients/{id}/documents` | `client.documents` (вложенно) **или** `query { documents(clientId: ID!) { ... } }` |
| `GET /clients/{id}/relatives` | `client.relatives` (вложенно) **или** `query { relatives(clientId: ID!) { ... } }` |

Сущности: `Client`, `Document`, `Relative`. Поля `documents`/`relatives` вложены в `Client` —
это и есть ключевая оптимизация: клиент + связанные объекты тянутся одним запросом. Дополнительно
оставлены top-level queries `documents`/`relatives` для явного 1:1-соответствия REST-эндпоинтам.
Для дат введён кастомный скаляр `Date` (в Swagger — строки).

## Примеры запросов (гибкость выбора полей)

**1. Минимальный список (например, выпадающий список в UI) — только имя:**
```graphql
query {
  client(id: "42") {
    id
    name
  }
}
```

**2. Полная карточка одним запросом — клиент + документы + родственники (заменяет 3 REST-вызова):**
```graphql
query {
  client(id: "42") {
    id
    name
    age
    documents { type number issueDate expiryDate }
    relatives { relationType name age }
  }
}
```

**3. Сценарий «только документы» (прямой аналог GET /clients/{id}/documents):**
```graphql
query {
  documents(clientId: "42") {
    type
    number
    expiryDate
  }
}
```

## Как GraphQL оптимизирует взаимодействие с client-info
- **Меньше round-trip / RPS:** связанные объekты, ранее запрашиваемые отдельными REST-вызовами,
  берутся за один запрос (пример 2 заменяет 3 вызова).
- **Нет over-fetching:** из ~500 атрибутов передаются только запрошенные поля ⇒ меньше объём, быстрее
  отклик (важно для мобильного веба).
- **Нет under-fetching и зоопарка эндпоинтов:** не нужен ни «толстый» ресурс, ни отдельный эндпоинт
  под каждый сценарий — один типизированный контракт, новые сценарии добавляются без изменения API.

*(На стороне сервера для связанных полей применяется батчинг — DataLoader, чтобы избежать проблемы N+1.)*
